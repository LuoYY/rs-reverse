## 2. 攻坚时间线与已实现突破

### 阶段 1：query 纯算法完全破解（2026-07-31）
- **query 结构**：119 字符 = '0' + numarr2string(88 bytes, basestr)
- **88 字节** = [CRC32(4B 大端)] [1] [0] [48] [session_data 48B] [32] [request_data 32B]
- **前 4 字节是 CRC32 校验和**（非随机 nonce），CRC32(bytes[4..87])，16/16 验证通过
- **session_data = keys[2] 原始 48B**（非加密！），跨 URL/请求固定
- **request_data = encryptMode1(plain24, numarrAddTime(keys17,now,random)[0], flag=0)**
- **plain24 = [keys2[0:8]^PREFIX_MASK 8B][rand×5][rand×3][0xb7,rand×2][rand][CRC32(url.toUpperCase())]**
- **PREFIX_MASK = [0x0b,0x16,0x00,0x10,0x00,0x31,0x00,0x01]**
- 纯 Node 端到端 18/18 全 200（3 会话 × 6 请求）

### 阶段 2：cookie 纯算法构造打通（2026-08-02，脚本 500-534）
- **cookie 完整生成流程（已验证 200）**：
  keys2/keys17（cd 派生）→ basearr（缺口）→ numarrEncrypt→xor(keys2,16)→encryptMode1(keys17+time)→be → nextarr=[4,8,r2mka,start,48,keys2,flag(0x80|len>>8),len&255,...be] → cookie='a'+numarr2string(encryptMode1([uuid(nextarr),...nextarr],keys16arr,1))
- **526 号决定性**：Node 重加密 cookie（uuid 重算 + encryptMode1）+ 挑战 O + Node query → **200**！

## 4. 踩坑经验（完整清单）

### 4.1 反重放假象（最大坑）
- **现象**：同 URL 窗口内重复请求 → 412，掩盖真实校验结果
- **发现**：526 号发现"重构 cookie 412"是反重放（不同 URL 变体第一次请求 200）
- **教训**：
  - 测试必须**每个变体用不同 path**（不同 URL 的 url_crc 不同 → 不触发反重放）
  - 或**每会话只测一个变体（第一次请求）**
  - 646 号的 400 是反重放假象（同会话多次请求）；624 号的 412 也可能是反重放
  - 649 号"每会话第一次请求"才得到真实结论（改 [25-28] 任意值 → 412）

### 4.2 [5000万] 200 假象
- **现象**：555/557 号改 [25-28]=5000万 → 200（两次），但 558 号同值 → 412
- **原因**：可能是 O cookie 偶然匹配 / 服务器状态 / 测量假象
- **教训**：单次 200 不可靠，必须多次复现 + 对照实验

### 4.3 crc32 hash 假阳性
- **现象**：644 号 crc32 返回 4 字节，`slice(4,8)` 是空数组，`empty.every()` 对空数组返回 true → 全匹配假象
- **教训**：hash 截断测试必须检查 slice 长度（≥4）

### 4.4 huffman 流式编码
- **现象**：改 basearr[i] → i 起编码全变（流式）。码长相同则总长度不变（服务器能解析），码长不同则 be 长度变
- **关键**：0x00 码长 6、0x01-0xFE 码长 8（或 9）、0xFF 码长特殊
- **0x00 结尾 → 400**（be 长度变 → 服务器走业务路径）；同码长替换 → 412（WAF 内容校验）

### 4.5 jsdom 结构不兼容
- jsdom basearr（150B）≠ 浏览器（168B）——**环境指纹段长度差 18B**
- jsdom 值域完全不同（0x38-0x3c 为主 vs 浏览器 0x00-0xff 分布）
- 只替换 [0-23] 无法对齐（[24+] 的 jsdom 环境指纹段与浏览器错位）

### 4.6 字节码反编译定位坑
- **641/650 号**：`_$kv` 源码的 while(1) 提取到的是初始化循环（648 字符，8 个操作码），主 dispatcher 在嵌套 if 树（75 个操作码分散）
- **635 号**：入口函数体结束定位错误（`lastIndexOf('},')` 找到函数体内位置）
- **639 号修正**：用末尾 `]);` 反向括号匹配定位调用
- **628 号 eval 定位**：调用栈 `eval at <anonymous>:6/7/10` = 外层 JS 行号（第 6 行 _$kv、第 7 行 _$hY）

### 4.7 keys17 加密异常
- encryptMode2(dec22, keys17) 输出 len=0（keys17 21 字节非 16 倍数 → 异常）
- xb 的 seg6 用 numarrAddTime(keys16)[0]（16→21），不是直接用 keys17

### 4.8 浏览器环境值采集失败
- 部分会话 envB 采集失败（页面导航/资源占用）
- 620-622 号浏览器枚举 window 全 keys 卡死（需限制数量）

## 6. 核心认知（突破性发现）

### 6.1 瑞数两层 VM 架构
- **外层 VM**：`_$kv` 解释器执行 `_$_$[1]`（bytecode），生成 cp 数组 + 反编译内层代码（`_$hY`）
- **内层 VM**：dynCode（cp[3]），执行时构造 basearr/cookie
- **xb vs nx 差异**：xb 的 basearr 由**外层 Coder**（len243.js 人工逆向）生成；**nx 的 basearr 由内层 VM 构造**（632 号证明）——这是 nx 不能直接复用 xb len243.js 的根源

### 6.2 服务器校验机制
- **412 = WAF 挑战层**：cookie 结构/绑定值校验（解密 basearr → 用 keys+环境指纹段重算 [25-28]）
- **400 = 业务层**：WAF 已过，业务数据错
- **反重放**：同 URL 窗口 ~60-85s → 412

### 6.3 绑定字节本质
- **[25-28] = f(keys, 环境指纹段[0-23])**，内容精确校验
- [0-23] 跨会话稳定 → 可硬编码（像 xb 的 seg0Override）
- [29-32] = `a7 54 9e ab` 跨会话稳定
- 动态字段：[25-28]、[69]、[73-116]（keys22 相关）、[84-87]

### 6.4 xb vs nx 服务器策略差异
- **xb 宽松**：len243.js 用随机 execNumberByTime（1500-2000）也 100% 通过
- **nx 严格**：绑定字节 [25-28] 内容精确校验（服务器用 keys 重算）
- 这是"xb 纯算法可行、nx 纯算法难"的根本原因

### 6.5 纯算法完整方案（最后缺口 = f 公式）
```
浏览器[0-23]环境指纹段硬编码 + cd派生keys → f公式重算[25-28] → basearr → 重构cookie
```
f 公式需反编译 dynCode 内层 VM 的 basearr 构造代码（`_$pg`→`_$$p[103]` 函数池内部逻辑）

## 8. 经验复盘与教训

### 8.1 为什么突破瑞数 JSVMP 耗时太久（核心反思）
1. **反重放假象浪费大量时间**：多次把反重放 412 误判为内容校验/值不匹配（624/646 号）。**正确方法学：每变体不同 path 或每会话第一次请求**。
2. **过早深入 keys 算法假设**：花大量时间测 MD5/SHA/CRC32/encryptMode/XXTEA（582-625 号 20+ 脚本），但 [25-28] 依赖环境指纹段（非纯 keys）——**应先做 jsdom vs 浏览器对照（653 号）定位本质**。
3. **xb 方法直接复用的误区**：xb 的 len243.js（numarrJoin 段标记）假设 nx 也适用，但 nx 是扁平结构 + 内层 VM 构造。**应先用调用栈/结构分析确认架构差异（632 号）**。
4. **execNumberByTime 假设的反复**：多次误判 [25-28] = 循环次数（数量级/范围），最终确认非 execNumberByTime。
5. **jsdom 环境注入的价值被低估**：559 号 jsdom 注入后 [12-23] 匹配浏览器，但没及时推进到 [25-28] 生成逻辑。

### 8.2 正确的方法学（供后续站点复用）
1. **测试方法论**：所有服务器行为测试必须**排除反重放**（不同 path / 第一次请求）
2. **对照实验优先**：jsdom vs 浏览器（同 nsd/cd）对照 → 快速定位"环境依赖 vs keys 依赖"
3. **架构先行**：先理解 VM 架构（解释器/反编译器/bytecode 池/内层构造），再针对性逆向
4. **数据驱动**：多会话数据集（keys + basearr）是逆向基础
5. **字节码反编译正确路径**：
   - 提取 bytecode 池（IIFE 调用参数）
   - 理解解释器（_$kv）操作码语义
   - 反编译目标子程序（_$_$[1] → cp 数组）
