## Query 参数逆向进展

### 结构已完全解析
- 88 字节 = numarrJoin 输出：`[nonce 4B][1][0][48][session 48B][32][request 32B]`
- session_data (48B = 3 AES blocks)：同会话固定
- request_data (32B = 2 AES blocks)：每请求变化
- nonce (4B)：每请求随机

### 加密密钥不在 cd keys 中
- 用所有 45 个 keys 尝试 AES-CBC 解密 session_data 和 request_data → 全部失败
- keys16/17/18/2 均无法解密
- nonce 作为 IV 也无法解密
- **结论：query 使用独立密钥体系，密钥由 RS 动态代码运行时生成**

## Query 参数沙箱启用分析（opcode-patcher agent）

### 核心发现
- RS hook prototype.open/send 成功，在 XHR 实例上设置 trampoline 函数 + 布尔 flag=false
- 强制 flag=true 后，RS.send 调用 trampoline(body)，但 trampoline 返回**空字符串**（非 undefined）
- Patch VM 退出码 if(exitCode===1)→if(true)：trampoline 返回值仍为空字符串
- 移除所有 catch{...=""} 块：无异常暴露 → 不是 catch 吞错误
- **根因**：trampoline VM 的 query 生成路径依赖 RS 内部"已验证"状态
  - 沙箱 cookie 被 400 拒绝（sandbox_keygen.js 不经管线 numarr2string.js 修复）
  - RS 无法从服务器获得 200 确认 → "已验证"状态从未设置
  - VM 内部条件判断评估为 false → query 生成逻辑跳过 → 返回空字符串

### VM dispatcher 结构
- 6 个 VM 解释器（while(1) + 二叉 if 树），函数名每次会话随机化
- 主 VM（L1）~72K 字符，包含 cookie/密钥/query 生成主逻辑
- trampoline 调用 VM_DISP(vmCtx, 0, bytecodeLen, argsArray)
- vmCtx 含 bytecode/scope/closure vars/cache flag

### 下一步路径
1. 修复沙箱 cookie 通过率（sandbox_keygen.js cookie 生成不经管线修复）
2. 用 Patchright 获取浏览器真实 cookie → 第二遍沙箱
3. CDP 断点提取"已验证"状态的具体存储位置

### 根本问题
- Go Coder 生成的 coder.code 与 JS 有微小差异（即使 nsd 相同）
- codeUid 使用 uuid（CRC32），1 字节差异 → 完全不同的 hash → 412
- 3% 通过率 = 偶然匹配
- 深层原因：500+ 行 Go Coder 中某处字符串拼接/格式化与 JS 不完全一致

### 实际可行方案：goja 运行 Coder
- goja = 纯 Go JS 引擎（无外部依赖）
- 用 goja 运行 Coder.js（获取 codeUid + functionsNameSort）
- 其他全部用原生 Go（keys, basearr, cookie, HTTP）
- 100% 准确率 + 零外部进程依赖

## 纯 Go 100% 通过率达成（2026-07-30 凌晨最终）

### 根因定位：Coder 逐字节对比

- 工具：`compare_coder.go`（Go）+ `js_dump_coder.js`（JS）

### 两个致命 bug
1. **`"++];"` 误写为 `"++;"`**：while 循环字符串少了一个 `]`，导致 coder.code 从 149818 开始全部偏移 1 字节 -> codeUid 完全错误 -> 412
2. **`"$_ts"` 被 sed 误替换为 `"Ts"`**：`sed 's/\$_ts/Ts/g'` 替换了字符串字面量 -> coder.code 末尾变量名错误

### 其他修复
