## Query 参数逆向进展

### 结构已完全解析
- 88 字节 = numarrJoin 输出：`[nonce 4B][1][0][48][session 48B][32][request 32B]`
- session_data (48B = 3 AES blocks)：同会话固定
- request_data (32B = 2 AES blocks)：每请求变化
- nonce (4B)：每请求随机

### 加密密钥不在 cd keys 中
- 用所有 45 个 keys 尝试 AES-CBC 解密 session_data 和 request_data → 全部失败
- keys16/17/18/2 均无法解密
- nonce 作为 IV 也无法解密
- **结论：query 使用独立密钥体系，密钥由 RS 动态代码运行时生成**

## Query 参数沙箱启用分析（opcode-patcher agent）

### 核心发现
- RS hook prototype.open/send 成功，在 XHR 实例上设置 trampoline 函数 + 布尔 flag=false
- 强制 flag=true 后，RS.send 调用 trampoline(body)，但 trampoline 返回**空字符串**（非 undefined）
- Patch VM 退出码 if(exitCode===1)→if(true)：trampoline 返回值仍为空字符串
- 移除所有 catch{...=""} 块：无异常暴露 → 不是 catch 吞错误
- **根因**：trampoline VM 的 query 生成路径依赖 RS 内部"已验证"状态
  - 沙箱 cookie 被 400 拒绝（sandbox_keygen.js cookie 生成不经管线 numarr2string.js 修复）
  - RS 无法从服务器获得 200 确认 → "已验证"状态从未设置
  - VM 内部条件判断评估为 false → query 生成逻辑跳过 → 返回空字符串

### VM dispatcher 结构
- 6 个 VM 解释器（while(1) + 二叉 if 树），函数名每次会话随机化
- 主 VM（L1）~72K 字符，包含 cookie/密钥/query 生成主逻辑
- trampoline 调用 VM dispatcher(vmCtx, 0, bytecodeLen, argsArray)
- vmCtx 包含：bytecode, scope, closure vars, cache flag

2. 用 Patchright 获取浏览器真实 cookie → 第二遍沙箱

### nextarr 结构修正
- 发现 numarrJoin 的第一个 []byte 参数也加长度前缀
- 正确结构：[2][8]time[48]keys2[highByte][baLen]basearrEncrypt
- keys2 从 nextarr[11] 开始（不是 nextarr[10]）
- 浏览器 keys2 ≠ 管线 keys2（RS 内部生成 vs 管线提取）

### 最终结论
**query 加密算法完全未知**，不是 AES 的任何模式，不是 RS 自定义 AES，不是 XOR/RC4。
密钥和算法在 JSVMP 闭包内部，需要反编译 VM bytecode 找到加密函数。
